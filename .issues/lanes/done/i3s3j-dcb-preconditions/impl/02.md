# 02 — Serialize postgres append preconditions

## Source
- plan/02-implementation-plan.md
- plan/checks/02-plan-sanity.md

## Goal

Make postgres append enforce the same option-presence semantics as the other adapters and serialize the precondition check plus insert in one transaction-scoped append lock.

## Depends on
- 01.md

## Scope
- `src/adapters/postgres/index.ts`
- `src/adapters/postgres/event-store.test.ts`
- postgres test helpers already used by adapter tests, if needed

## Contract surfaces
- postgres `AppendOptions` semantics
- postgres transaction ordering
- transaction-scoped advisory append lock
- `ConcurrencyError` mapping for stale preconditions
- `onAfterInsert` projectors remain inside the append transaction
- `onAfterCommit` processors remain after commit

## Plan-check watch items
- Use a single helper or clearly duplicated adapter logic for option-present semantics so in-memory, filesystem, and postgres do not drift.
- Pick a stable postgres advisory lock key/name and keep the lock acquisition as the first statement inside the append transaction before `fetchMaxPosition(...)` or position allocation.
- Preserve the existing `ConcurrencyError` shape exactly while changing when it is emitted.

## Work
- Add focused failing postgres coverage for option-presence semantics:
  - present options with `expectedPosition: undefined` protect an empty tag boundary.
  - present options with `boundaryTags: undefined` protect the global stream boundary.
  - present options with `boundaryTags: undefined` and `expectedPosition: 0n` require global latest position `0n`.
- Add coverage that postgres append acquires a transaction-scoped advisory append lock before `fetchMaxPosition(...)`, position allocation, inserts, and `onAfterInsert` handlers.
  - Prefer a narrow transaction-query sequence test if the current harness cannot run a deterministic real race.
  - If a practical concurrent postgres integration test already exists or is easy to add safely, assert two stale writers cannot both commit.
- Update postgres precondition validation so only `options === undefined` skips the precondition.
- Use `options.boundaryTags ?? []` for boundary selection, preserving `undefined` and `[]` as global.
- Acquire the chosen transaction-scoped advisory lock as the first statement inside the `sql.begin(...)` callback.
- Keep the lock held through precondition check, position allocation, inserts, and `onAfterInsert` by relying on transaction-scoped release at transaction end.
- Ensure stale precondition failures still return the existing `ConcurrencyError` result path, not an uncaught exception.

## Acceptance
- Postgres append treats omitted `options` as no precondition.
- Postgres append treats present `options` as an active precondition even when `expectedPosition` is `undefined`.
- `boundaryTags: undefined` and `boundaryTags: []` select the global stream boundary.
- The advisory append lock is transaction-scoped and acquired before any precondition read or position allocation.
- The lock remains in effect through inserts and in-transaction projectors.
- Stale postgres appends return the existing `ConcurrencyError` shape.
