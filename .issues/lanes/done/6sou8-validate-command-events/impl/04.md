# 04 — Model command event candidates separately

## Source
- plan/03-transform-schema-command-event-contract-plan.md

## Goal
Make definition-backed commands expose a truthful candidate-vs-parsed event contract: `payload(ctx)` returns event payload schema input, direct `Command.event(ctx)` returns a pre-parse candidate, and `output(event, ctx)` remains parsed/stored output-shaped.

## Depends on
- none

## Scope
- `src/core/slice.ts`
- `src/core/event.ts` only if helper types must move near event definitions
- `src/index.ts` only if implementation proves a public helper export is needed
- `src/__tests__/type-check.ts`

## Contract surfaces
- public TypeScript DSL: `defineCommand` definition-backed overload
- exported `Command.event(ctx)` return type for definition-backed commands
- `output(event, ctx)` callback event type
- raw command `Command.event(ctx)` compatibility
- `EventDefinition.create(...)` remains output-payload, no-parse helper

## Intent / decision vocabulary
- `CommandEventCandidate`: event object produced from command context before optional schema parse
- `DefinitionBackedCommandPayloadInput`: definition-backed command payload builder return type using `z.input<TPayloadSchema>`
- `ParsedCommandEvent`: stored/output event accepted by `EventDefinition.schema`
- `RawInteropEvent`: raw command path where candidate and stored event are identical

## Plan-check watch items
- Keep `Command` candidate-vs-parsed event generics local and compatible with existing operation helper types (`OperationInput`, `OperationOutput`, `OperationError`) and `executeCommand` inference.
- Build definition-backed candidates directly with copied tags; do not call `EventDefinition.create(...)` with schema-input payload.
- Keep casts local to overload normalization and document any new cast per `doc/code-style.md`.
- Update direct `.event(ctx)` type-check assertion for transform schemas so it proves input/candidate payload, not stored/output payload.
- Keep object-schema examples/tests passing where input/output payload types are identical.

## Work
- Add focused failing type-level coverage first in `src/__tests__/type-check.ts`:
  - transform event payload schema where `z.input` is `string` and `z.output` is `number`
  - definition-backed command `payload(ctx)` returning `string` typechecks
  - definition-backed command `payload(ctx)` returning `number` fails with `@ts-expect-error`
  - `output(event)` sees `event.payload` as `number`
  - direct definition-backed `command.event(ctx)` sees candidate `payload` as `string`, not `number`
  - raw command form still sees candidate and stored event as same raw event type
- Introduce candidate-vs-parsed event typing in `src/core/slice.ts`, using a trailing default generic or equivalent compatibility seam so raw commands keep current type shape.
- Change definition-backed command payload builder typing from stored/output payload to schema input payload.
- Construct definition-backed event candidates directly with `{ type, tags: [...tags(ctx)], payload }` instead of `EventDefinition.create(...)`.
- Preserve `EventPayloadOf<TDefinition>`, `EventOf<TDefinition>`, and `EventDefinition.create(...)` output-payload semantics.
- Export new helper types only if type tests or public API ergonomics prove they are needed; otherwise keep helpers internal.

- Definition-backed command `payload(ctx)` is typed as schema input for transform payload schemas.
- Definition-backed direct `Command.event(ctx)` returns a pre-parse candidate with schema-input payload.
- Definition-backed `output(event, ctx)` receives `EventOf<TDefinition>` with schema-output payload.
- Raw command `Command.event(ctx)` remains type-compatible with existing raw event behavior.
- `EventDefinition.create(...)` still accepts output payload and is not used for definition-backed candidate construction.
- Existing operation helper type inference still works.
