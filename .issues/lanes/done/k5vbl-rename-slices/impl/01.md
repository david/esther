# 01 — Add canonical operations AppConfig contract

## Source
- plan/01-implementation-plan.md
- plan/checks/01-plan-sanity.md

## Goal

Make `createApp({ operations: [...] })` work as the canonical configuration path, keep `slices` working as a deprecated alias, and reject configs that provide both keys.

## Depends on
- none

## Scope
- `src/core/app.ts`
- `src/core/app.test.ts`
- `src/__tests__/type-check.ts`
- `src/index.ts` only if public export wiring needs adjustment

## Contract surfaces
- `AppConfig` public TypeScript API
- `createApp(config)` runtime API
- deprecated `slices` compatibility alias
- mixed-config validation error
- dispatch behavior remains unchanged

## Intent / decision vocabulary
- `configureDispatchableOperations`
- `acceptDeprecatedSlicesAlias`
- `rejectMixedOperationConfig`
- `dynamicDispatchUnchanged`

## Plan-check watch items
- Use explicit key-presence checks in `createApp` resolver; empty `operations: []` and `slices: []` must be valid, mixed keys must reject.
- Watch `exactOptionalPropertyTypes`; if `operations?: undefined` / `slices?: undefined` gets awkward, use local branch types that still reject both real keys and neither key.
- Keep at least one runtime test and one type test for deprecated `slices` alias.
- Do not rename exported `DispatchFn`, adapter request fields, Fastify route config, `OperationName`, `RegisterableOperation`, or unknown-slice error text.

## Work
- Add focused failing runtime tests in `src/core/app.test.ts` for:
  - `createApp({ eventStore, operations: [pingQuery] })` dispatching like the old `slices` config.
  - legacy `slices` still dispatching.
  - configs with both `operations` and `slices` throwing exact mixed-config error.
  - empty `operations: []` creating an app and preserving `Unknown slice: ...` for unknown dispatch.
- Add type-level expectations in `src/__tests__/type-check.ts` for:
  - `AppConfig` accepts `operations`.
  - deprecated `slices` alias still typechecks.
  - object literal with both keys gets `@ts-expect-error`.
  - object literal with neither key gets `@ts-expect-error`.
- Refactor `AppConfig` in `src/core/app.ts` into a shared base plus `operations` and deprecated `slices` branches.
- Add a small resolver near `createApp`, using key-presence checks rather than truthiness.
- Destructure or loop over resolved operations; low-risk local variable rename from `slice` to `operation` is allowed.
- Preserve dispatch signature, `DispatchFn`, adapter contracts, `RegisterableOperation`, `OperationName`, and `Unknown slice: ...` error text.

## Acceptance
- `createApp({ eventStore, operations: [...] })` works and dispatches operation names exactly like `slices`.
- `createApp({ eventStore, slices: [...] })` still works and is marked deprecated in TypeScript docs.
- `createApp(...)` rejects both keys with deterministic error: `AppConfig cannot define both operations and slices; prefer operations` unless implementation finds an existing project convention and records why.
- Empty `operations: []` is valid.
- Unknown dispatch target still throws current `Unknown slice: ...` text.
- Type-level coverage rejects both keys and neither key for object literals.
