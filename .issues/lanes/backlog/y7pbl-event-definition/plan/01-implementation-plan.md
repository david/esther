# Implementation Plan — `defineEvent` event definition helper

## Goal

Add additive core DSL helper that lets app code define each domain event once, then derive event schema, constructor, full event type, and payload type from that value.

Primary user shape:

```ts
const BookingCreated = defineEvent({
  type: "BookingCreated",
  payload: z.object({
    bookingId: z.string(),
    propertyId: z.string(),
    tenantId: z.string(),
  }),
});

type BookingCreated = EventOf<typeof BookingCreated>;
type BookingCreatedPayload = EventPayloadOf<typeof BookingCreated>;
```

## Non-goals

- Do not remove or deprecate `DomainEvent`.
- Do not change stored event shape, append semantics, event-store APIs, or hook timing.
- Do not infer/generate DCB tags.
- Do not make command event construction parse/throw for normal domain flow.
- Do not redesign reducer/read-model/processor APIs to accept event definitions directly; users pass `Event.schema` in this slice.
- Do not add event versioning policy.

## Behavior changes

| Behavior | Before | After |
|---|---|---|
| Define event | separate TS type + Zod object | one `defineEvent({ type, payload })` value can produce both |
| Construct event | object literal in command `event(ctx)` | optional `Event.create({ tags, payload })` constructor |
| Validate persisted event | hand-written schema parse | generated `.schema` parse; same serialized shape |
| Existing user code | raw schemas and `DomainEvent` aliases required | raw schemas still work; helper is preferred ergonomic path |

Details:

- Add new `src/core/event.ts` as canonical event-definition module.
- Add root exports from `src/index.ts` for `defineEvent`, `EventDefinition`, `EventOf`, and `EventPayloadOf`.
- Keep all existing schema-consuming DSLs unchanged.
- `defineEvent(...).create(...)` returns object only; it must not call `.parse(...)`.
- `create(...)` defensively copies `tags` with `[...input.tags]`; payload reference stays caller-owned, same as today object literals.

## Event model changes

| Event | Status | Producer | Consumers affected | Payload delta | Validation delta | Replay / migration |
|---|---|---|---|---|---|---|
| all user domain events | unchanged serialized shape | command `event(ctx)` callbacks | reducers, read-model event bindings, processors, event stores | same | same schema parse behavior; schema may be generated by helper | replay-safe; no stored event migration |

Serialized event shape remains:

```ts
type DomainEvent<TType extends string, TPayload> = {
  readonly type: TType;
  readonly tags: ReadonlyArray<string>;
  readonly payload: TPayload;
};
```

Generated schema must parse same runtime shape:

```ts
z.object({
  type: z.literal(definition.type),
  tags: z.array(z.string()),
  payload: definition.payload,
});
```

Replay/projector implications:

- Historical events remain valid if their hand-written schema was equivalent.
- Projectors/processors still filter by extracted event type string.
- No backfill, migration, checkpoint reset, or replay order change.

Proposed public shape:

```ts
export type EventDefinition<
  TType extends string,
  TPayloadSchema extends z.ZodType,
> = {
  readonly type: TType;
  readonly payloadSchema: TPayloadSchema;
  readonly schema: z.ZodType<DomainEvent<TType, z.output<TPayloadSchema>>>;
  readonly create: (input: {
    readonly tags: ReadonlyArray<string>;
    readonly payload: z.output<TPayloadSchema>;
  }) => DomainEvent<TType, z.output<TPayloadSchema>>;
};

export type EventOf<TDefinition extends EventDefinition<string, z.ZodType>> =
  TDefinition extends EventDefinition<infer TType, infer TPayloadSchema>
    ? DomainEvent<TType, z.output<TPayloadSchema>>
    : never;

export type EventPayloadOf<TDefinition extends EventDefinition<string, z.ZodType>> =
  TDefinition extends EventDefinition<string, infer TPayloadSchema>
    ? z.output<TPayloadSchema>
    : never;

export function defineEvent<
  const TType extends string,
  TPayloadSchema extends z.ZodType,
>(definition: {
  readonly type: TType;
  readonly payload: TPayloadSchema;
}): EventDefinition<TType, TPayloadSchema>;
```

Implementation constraint:

- Prefer no casts. If Zod generic constraints force one cast for `.schema`, keep it local to `src/core/event.ts`, document why, and keep output as `DomainEvent<TType, z.output<TPayloadSchema>>` only.

## Testing contract

Focused runtime tests:

- Add `src/core/event.test.ts` for:
  - `defineEvent(...).type` equals literal name.
  - `.payloadSchema` is original payload schema value.
  - `.schema.parse({ type, tags, payload })` succeeds for matching event.
  - `.schema.safeParse(...)` rejects wrong `type` literal.
  - `.create({ tags, payload })` returns `{ type, tags, payload }`.
  - `.create(...)` copies tags defensively.
- Add/extend processor/read-model/reducer coverage proving:
  - `processorEvent({ schema: Event.schema })` filters and handles matching stored events.
  - `readModelEvent({ schema: Event.schema })` projects matching stored events.
  - `defineReducer({ schemas: [Event.schema] as const })` folds typed event union.

Type-level tests in `src/__tests__/type-check.ts`:

- `defineEvent({ type, payload })` preserves event type literal.
- `EventOf<typeof BookingCreated>` is assignable to `DomainEvent<"BookingCreated", Payload>`.
- `EventPayloadOf<typeof BookingCreated>` equals payload schema output.
- `.create(...)` requires payload fields and rejects mismatched payload types.
- Command `event(ctx)` can return `BookingCreated.create(...)` when command event type is `EventOf<typeof BookingCreated>`.
- Reducer `event` parameter narrows on `event.type` when schemas come from event definitions.
- `readModelEvent` and `processorEvent` handler events infer payload from `.schema`.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Zod generic type too hard to express without cast | keep any unavoidable cast inside `src/core/event.ts`; document exact schema output contract; cover with type-check tests |
| Event definition accepted directly by reducer/read-model/processor by accident | keep signatures schema-based; tests/examples pass `.schema` explicitly |
| `.create(...)` starts runtime validation/throws | implementation must only return object; tests and review check no `.parse` call |
| Event extraction behavior changes for invalid schemas | preserve existing messages or update tests intentionally with clearer generic wording |
| Root export omission makes API hard to discover | export helper and types from `src/index.ts`; add import coverage in type-check test |

## Acceptance criteria

- `defineEvent`, `EventDefinition`, `EventOf`, and `EventPayloadOf` are exported from package root.
- Event definition object exposes `type`, `payloadSchema`, `schema`, and `create`.
- Generated `.schema` validates `{ type, tags, payload }` with literal event type and supplied payload schema.
- `.create(...)` returns same serialized event shape and copies tags.
- Existing raw Zod event schemas and `DomainEvent` aliases still work without source changes.
- Reducer, read-model event binding, and processor event binding work with `Event.schema`.
- Type-check suite proves payload/type inference and mismatch failures.
- `bun run test`, `bun run typecheck`, and `bun run lint` pass.

## Implementation notes

- Keep helper in `src/core/event.ts`; do not put it in `types.ts` if it needs runtime `zod` import and helpers.
- Keep app-module callback purity unchanged; helper has no I/O.
- Update imports in examples/tests to use package root where public API is being proven.
- Use `z.output<TPayloadSchema>` for event payload type; do not infer from a separately declared payload interface.
- Keep `tags` input type `ReadonlyArray<string>` and returned event `tags` read-only by type.
- Low-risk mechanical conversions of tests/examples can be minimal; do not mass-convert every existing event schema.
- At implementation checkpoints, watch for drift into direct `EventDefinition` acceptance; that belongs to later issue.
