# 03 — Dispatch explicit Fastify routes through the dynamic boundary

## Source
- plan/01-implementation-plan.md
- plan/checks/01-plan-sanity.md

## Goal

Make configured Fastify routes execute by calling the existing dynamic `DispatchFn` with the configured slice name and mapper-produced input, while preserving wildcard fallback behavior and default result/error mapping.

## Depends on
- 02.md

## Scope
- `src/adapters/fastify/input.ts` and any cohesive colocated Fastify route/result helper module extracted from it
- `src/__tests__/fastify-input.test.ts` or a colocated Fastify adapter test
- No changes to `src/core/app.ts`, `src/core/input-adapter.ts`, event stores, read models, processors, or effect adapters except compatibility checks if needed

## Contract surfaces
- Fastify explicit HTTP route registration
- Existing `DispatchFn(sliceName: string, input: unknown)` dynamic boundary
- Shared default Fastify result mapping: success `{ data }`, `SchemaError` 400, `ReadModelNotFound` 404, `ConstraintError`/`ConcurrencyError` 409, unknown errors 422
- Wildcard `app.all("/*")` fallback remains available when no explicit route matches

## Plan-check watch items
- Explicit routes must call `boundDispatch(route.slice, mappedInput)` and must not create a second execution path or bypass schema validation.
- Share or extract the default Fastify result mapping so explicit routes and wildcard routes cannot drift.
- Keep existing no-routes wildcard behavior source-compatible.
- Keep casts local to the typed-adapter bridge and document why they are safe under the dynamic dispatch boundary.

## Work
- Add failing runtime tests first for a configured explicit route whose URL path differs from the slice name and verify the captured dispatch call uses the configured slice.
- Add a runtime test showing the explicit route mapper receives body, query, params, headers, method, url, and request, and that its return value is passed to dispatch.
- Add explicit-route default response tests for success and known framework errors using the same expectations as the wildcard handler.
- Add or preserve no-routes wildcard tests proving URL-path-derived slice names and GET query/non-GET body input still work without `routes`.
- Refactor the existing Fastify default result mapping into a local helper if needed, then register explicit routes before the wildcard handler.
- Ensure unbound explicit route handling still throws `Fastify adapter not bound to app`.
- Run focused Fastify tests and typecheck.

## Acceptance
- Configured explicit Fastify routes dispatch the configured slice name, not a name derived from the route URL.
- Explicit route `input` mappers receive the documented request context and their returned value is passed to `DispatchFn` as `unknown`.
- Explicit routes use the existing default success and error response mapping when no `respond` override is configured.
- Fastify wildcard dispatch remains available and tested when `routes` is absent or no explicit route matches.
- Unbound explicit routes fail with the existing `Fastify adapter not bound to app` error behavior.
