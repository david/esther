# 04 — Support typed Fastify response overrides and final compatibility

## Source
- plan/01-implementation-plan.md
- plan/checks/01-plan-sanity.md

## Goal

Complete optional typed Fastify response override behavior and finish compatibility verification for the typed adapter-binding feature without adding a typed in-process app client or changing core execution semantics.

## Depends on
- 03.md

## Scope
- `src/adapters/fastify/input.ts` and any colocated route/result helper module from earlier tasks
- `src/__tests__/fastify-input.test.ts`
- `src/__tests__/type-check.ts`
- Public exports touched by earlier tasks, only if final export consistency fixes are needed

## Contract surfaces
- Optional Fastify route `respond` callback runtime behavior
- Typed response override context: selected `Result`, request context, and `FastifyReply`
- Default response mapping remains unchanged when `respond` is absent
- No public `app.client`, `app.execute`, typed in-process dispatch facade, event/read-model/persistence/processor/effect changes

## Plan-check watch items
- Do not silently drop optional typed `respond` support; if it proves disproportionate, stop and ask whether to split it before declaring acceptance complete.
- Optional `respond` must be opt-in and must not change default error/status mapping.
- Keep any casts local to the typed-adapter bridge and document why they are safe.
- Verify no public typed in-process app client was added.

## Work
- Add a failing runtime test first showing an explicit route `respond` callback receives the route result and can override the response body/status.
- Add or tighten compile-only assertions that the `respond` callback sees the selected command/query result type.
- Implement `respond` invocation only for explicit routes that configure it; otherwise use the shared default result mapper from task 03.
- Ensure the `respond` context includes the same request context shape as the input mapper and the Fastify `reply` object.
- Re-check that schema/runtime validation remains owned by core dispatch by preserving or adding an explicit-route `SchemaError` default mapping test.
- Review public exports and type tests for accidental `app.client`, `app.execute`, or narrowed `App.dispatch` APIs; remove any such drift.
- Run full repo gates.

## Acceptance
- Explicit Fastify routes with `respond` can override response handling and receive the selected slice result plus request/reply context.
- Explicit Fastify routes without `respond` keep the default success/error mapping from the wildcard handler.
- Type-check coverage proves `respond` is typed to the selected command/query result.
- The feature remains adapter-bound: `App.dispatch`, `DispatchFn`, and `InputAdapterBinding.bind` stay dynamic and no public typed in-process client is introduced.
- Full gates pass.

## Manual verification
- Concrete CLI scenario after implementation:
  - configure a route with `respond: ({ result, reply }) => reply.status(result.isOk() ? 201 : 499).send({ custom: result.isOk() })`;
  - bind dispatch to return `ok({ id: "b1" })`;
  - inject the configured route and expect status 201 with `{ custom: true }`;
  - regression check: inject a similar explicit route without `respond` and expect the default `{ data: { id: "b1" } }` body and status 200.
